# PR 3b-1: só Pix e "pagar sem medo" (a entrada da proposta, a falha fechada no lugar do 50, a tela do Pix na ordem nova)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A tela da entrada do `/orcamento` passa a ser só Pix (pela chave `MP_METODOS`), cobra sempre o percentual
gravado na proposta (sem o 50 de reserva, nem no banco nem na tela), mostra o Pix na ordem nova com o nome que aparece
no banco ("Fernando Ferreira Dos Santos") e responde, antes de pagar, só as perguntas que já são verdade hoje.

**Architecture:**
- **Só Pix:** uma chave só, `MP_METODOS`, a mesma da tarefa A7 do plano da Cloudflare
  (`03 Projetos/site/docs/superpowers/plans/2026-10-21-migracao-cloudflare.md`, "Task A7: só Pix fora do local").
  `configPagamentos` ganha `metodos` (`metodosDe(env, amb)`), `configPublica` o expõe, `servico.iniciar` recusa o
  cartão ANTES do banco e a tela esconde o seletor inteiro. Se a A7 já estiver na base quando este plano rodar, a
  Task 1 só confere e faz a parte da tela. O código do cartão fica no repositório, desligado.
- **Entrada da proposta:** o banco troca `coalesce(pr.sinal_percentual, 50)` por falha fechada (23514, nenhuma cobrança
  criada) numa migration nova que redefine `app.pagamentos_iniciar_tentativa`. O servidor traduz esse 23514 em 409 com
  o WhatsApp. A tela lê o percentual por um módulo puro novo, `js/orcamento-pix.js` (`window.BZPix`), testado sem DOM;
  sem percentual, não cobra. O rascunho da tabela passa a 40.
- **Tela:** o bloco `#o-pix` é refeito na ordem da spec (valor e percentual → nome no banco → "Copiar o código Pix" →
  3 passos), o status logo abaixo, e o QR vai para um `<details>` "Pagar por outro aparelho (QR Code)", fechado no
  celular e aberto a partir de 768 px. Uma seção nova, `#o-antes` ("Perguntas antes de pagar"), aparece no resumo e
  na entrada, com `<details>` fixos, sem IA.
- **E2E:** o trecho do pagamento sai de `docs/e2e-orcamento.mjs` (905 linhas, acima do teto) para `docs/e2e-pix.mjs`
  (`passoDoPix`), que lê do servidor se o cartão vale e roda os dois caminhos.

**Tech Stack:** Node 24 (ESM, `node:test`), PGlite com as migrations reais (`docs/testes/_banco.mjs`), JS de navegador
sem build (IIFE, `window.BZ*`), CSP sem inline, Playwright no E2E.

**Spec:** `docs/specs/2026-10-21-pr3b-vender-sozinho.md` (revisão 2): §4 inteira ("Só Pix e 'pagar sem medo'"), §3

   A ENTRADA POR PIX na página /orcamento (PR 3b-1; spec 2026-10-21 §3 e §4):

(function () {
  'use strict';
  var QR_ABERTO_DESDE_PX = 768;
  function percentuais(pr) {
    var p = pr ? pr.sinal_percentual : null;
    if (typeof p !== 'number' || !Number.isInteger(p) || p < 1 || p > 100) return null;
    return { entrada: p, restante: 100 - p };
  }
  /* a mesma conta do banco: round(total × pct / 100, 2) */
  function valorDaEntrada(pr) {
    var pc = percentuais(pr), total = pr ? Number(pr.valor_total) : NaN;
    if (!pc || !(total > 0)) return null;
    return Math.round(total * pc.entrada) / 100;
  }

  function qrAbertoEm(larguraPx) { return Number(larguraPx) >= QR_ABERTO_DESDE_PX; }

## Dúvidas para o controlador

1. **Quem faz a A7.** Hoje (`28d8de8`) a A7 não está na `main`, e a do plano da Cloudflare usa o `ambienteDe` da A1
   (`BZ_PLATAFORMA`), que também não existe. A Task 1 a faz aqui com o mesmo nome e a mesma interface, com o teste no
   ambiente da Vercel de hoje; se a Cloudflare mesclar antes, a Task 1 só confere. Precisa ser combinado com a sessão
   do plano (a spec §4 diz isso).
2. **O simulado também obedece `MP_METODOS`.** A A7 diz "no retorno simulado, `metodos: [...METODOS]`", mas o próprio
   passo de E2E dela pede um servidor local com `MP_METODOS=pix` sem cartão. Fiz `metodosDe(env, 'local')`: ausente =
   os dois (o E2E do cartão segue), `pix` = só Pix.
3. **O seletor some inteiro**, não só o botão do cartão (a A7 esconde só o botão): um grupo de rádio de uma opção não
   ajuda, e a spec §4 diz "a tela esconde o seletor".
4. **Falha fechada também para 0%,** não só para nulo: um Pix de R$ 0 não existe, e a regra de preços já exige 1 a 100.
5. **O contrato já fala em prazo "contado do sinal pago e do material recebido"** (`api/_vendas/escopo.mjs`, conferido
   em `docs/testes/alteracoes.test.mjs:69`). A spec trata essa regra como da oferta de lançamento (D4). Este PR não mexe
   no texto do contrato (fora do 3b-1), mas a contradição existe hoje e merece decisão (ou entra no 3b-2).
6. **A ordem do status.** Na spec, "Esperando o pagamento…" vem antes do QR. O status é um só para Pix e cartão, então
   o `<details>` do QR saiu de dentro de `#o-pix` e ficou logo depois do status.
7. **"Entrada" no lugar de "sinal"** só no texto que este PR reescreve (`#o-pag-lead`); o resto é do PR 4.
